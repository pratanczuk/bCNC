# Physical plotter testing — first stage

Target: `socket://192.168.0.22:8888`. User reported that the mat was inserted.

## Results

- TCP connection succeeds; realtime status replies are parsed correctly by the
  application's `LineFramer` and `status_report` implementations.
- Nine status queries across three connections succeeded with a two-second gap
  between connections. Median response time: 67.5 ms, observed range 15.5–153.8 ms.
- An earlier immediate reconnect timed out after its first connection returned
  three valid reports. A two-second gap avoided that failure in this test; the
  precise bridge timeout/connection handling remains to be investigated.
- The plotter consistently reports `Hold:0`, machine position `0,0,0`, zero
  feed/output, and `Pn:YZ`. Firmware identity and the meaning of those active
  inputs have not been established.
- Initial work offset report: `-215,4181.112,0`. No physical mat origin is verified.
- `$I`, `$G`, `$$`, `$#` queries received no replies while held. The reported RX
  space decreased by their combined 12 bytes, consistent with queued queries.
- Production discovery logic correctly produces no new queries while held.

No motion, pressure command, homing, unlock, resume or reset was sent. Connections
were closed after the checks. The earlier read-only queries remain unacknowledged.

## Blocked operation

Automatic approval review rejected a soft reset because it would discard the
held queue and testing authorization did not explicitly authorize clearing an
existing job. The reset script was prepared but was not executed.

Explicit approval to discard the paused job and soft-reset is needed before the
next stage. Afterward: identify firmware, inspect settings and inputs, establish
safe mat coordinates, verify blade lift, then perform bounded movement and a
small pressure/drag-knife test. Motion readiness has not yet been established.

Raw evidence: `2026-09-14-readonly.json`, `2026-09-14-status-test.json`.

Both squares used the production compiler/sender with M5 and **no Z or pressure
commands**. The compensation test used production knife geometry converted to
relative XY commands for a dry run. The old work offsets were preserved. These
checks establish controller-reported motion and protocol behavior, not measured
mechanical accuracy or cut quality.

During test development, one harness used a nonexistent `disconnect` service
method and its error cleanup reset the controller. Another preflight assertion
was too strict for the geometry engine's one-micrometre bounds expansion and
stopped before motion. Both harness errors were corrected; separate `verified`
logs contain the passing runs. No firmware settings were rewritten.

### Software fixes from testing

- Idle disconnect no longer invokes the hold/reset purge sequence when there is
  no running job or pending command. This avoids creating unnecessary paused or
  reset states; it does not prove why this device sometimes boots in Hold.
- Startup Hold now explains deliberate recovery through Advanced settings and
  warns against resuming an unknown queued job. No automatic reset was added.
- Full regression suite: **189 tests passed**.

## Stage 3 — small pressure cut completed

After the user confirmed sacrificial material and a clear test area, the actual
application cut-start path (`Application.run` → job preparation → detached
compilation → Sender) executed one compensated 10 mm square.

- Fresh work origin set using `G92 X0 Y0` at MPos `-215,0,0`.
- Test artwork spans approximately X/Y 4.75–15.25 mm within the confirmed
  20 × 20 mm area. Material feed: 300 mm/min; output command: S200 of 1000.
- Production knife geometry: 0.25 mm blade offset, 0.5 mm overcut; no Z commands.
  Geometry was compensated before submission; automatic compensation was disabled
  for this already-compensated test to avoid applying it twice.
- The complete application start/preparation/compilation/send/completion sequence
  passed. No alarm, rejected command or internal application error was reported.
- Observed peak controller output: 200. Final output: 0, with M5 confirmed through
  an independent post-disconnect query. Final position: `-215,0,0`; state: Idle;
  reported free buffers: 100 planner / 1024 RX bytes.
- Post-cut work offsets: G54 `-215,0,0`; G92 `0,0,0`. The obsolete 4181.112 mm Y
  offset has been cleared. Application preference files and firmware settings
  were not rewritten. The controller retains modal F300/S200 with output off.

## Automatic mat loading and unloading

Verified on the real FilmCut plotter at `socket://192.168.0.22:8888` through
Application.loadMat / unloadMat and the normal sender/monitor loop.

- Automatic board detection selected the FilmCut loader.
- Load: M5 acknowledged, X-only homing acknowledged and idle, material load
  completed, then G92 X0 Y0 acknowledged and fresh idle. Work X/Y verified zero.
- Loader reported a 119.1 mm sensor-edge search and positioning 20 mm from the
  trailing edge. This is the firmware's edge measurement, not a measured mat size.
- Unload: M5, X-only homing, successful material ejection, then G92.1, each gated
  on acknowledgment and a fresh idle report.
- Final state: Idle, MPos (-215, 42.924, 0), blade output 0, pins YZ (material
  sensor P cleared). Mat confirmation remains unchecked.
- No cut was performed and no firmware settings were changed.

Both operations passed. The mat is now unloaded and must be reinserted under the
rollers before another load. Evidence: `2026-09-14-mat-load-unload.json`.

Software failure tests cover missing sensor, unsupported firmware, homing errors,
loader warnings followed by `ok`, missing completion, stale idle reports,
connection loss, cancellation, timeout and excess travel. Timeout/cancel failure
paths were simulated, not deliberately triggered on the physical plotter.

## Requested over-travel alarm test

Triggered a real grblHAL `ALARM:2` with `G21 G90 G53 G1 X1 F60`, requesting
an X position beyond the far machine boundary. Temporarily enabled `$20=1`;
also enabled firmware check mode (`$C`) as independent protection against motion.
This tests a controller-generated soft-limit alarm, not physical contact with a
far-end switch or mechanical stop. Original `$20=0`, `$21=1`, X travel 216 mm.

The application displayed **This move is outside the working area**, guidance to
check origin/mat/design position, and a Review plotter action. Technical details
retained ALARM:2 and the controller's explanation. Mat movement was disabled and
alignment confirmation was cleared. Position remained (-215, 42.924, 0).
Screenshot visually inspected: `2026-09-14-overtravel-alarm.png`.

The test harness's first cleanup verification queried the app's settings cache
before rediscovery completed after reset, raising KeyError. An independent TCP
read confirmed `$20=0` had actually been restored. Explicit unlock, M5 and X
homing then completed successfully. Final independent verification: Idle,
MPos (-215,42.924,0), M5/S0, material sensor clear, `$20=0`, `$21=1`.
No application source changes were needed for the observed alarm presentation.

Evidence: `2026-09-14-overtravel-alarm.json`,
`2026-09-14-alarm-recovery-read.json`,
`2026-09-14-alarm-recovery-complete.json`.
